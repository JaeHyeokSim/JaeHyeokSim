# 심재혁 (JaeHyeokSim)

해외 상품 소싱 커머스 플랫폼을 **5년 8개월간 단일 개발자에 가까운 범위로** 만들고 운영해 온 백엔드 개발자입니다.
상품을 긁어오는 것부터 오픈마켓에 올리고, 주문을 받아 중국 창고를 거쳐 국내 배송까지 보내는
전 구간을 다뤘습니다.

관심사는 **"조용히 실패하지 않는 시스템"** 입니다.
수집·업로드·정산처럼 외부 사이트와 외부 API에 의존하는 작업은 반드시 실패하고,
그 실패가 눈에 보이지 않으면 데이터가 조금씩 어긋나기 시작합니다.
큐·재시도·멱등성·상태 추적을 습관처럼 붙이는 이유입니다.

## 대표 프로젝트

### [sourcing-pipeline](https://github.com/JaeHyeokSim/sourcing-pipeline)

`Java 21` `Spring Boot 4.1` `Spring Data JPA` `Flyway` `PostgreSQL` `Chrome Extension MV3`

실무에서 5년간 반복해서 부딪힌 문제들을 **처음부터 다시 설계한** 상품 수집 → 정규화 → 오픈마켓 등록 파이프라인.

- 브라우저(크롬 확장)가 수집하고 **서버가 큐와 동시성을 통제**하는 구조 — 확장이 여러 개 떠도 상한이 무너지지 않습니다
- **lease 기반 점유 + 만료분 자동 회수** — 탭이 죽어도 작업이 영원히 `RUNNING` 으로 남지 않습니다
- **일시 실패(지수 백오프 재시도)와 영구 실패(즉시 확정)를 구분**
- `(사이트, 상품ID)` 유니크 + upsert 로 재수집 멱등, 원본 페이로드는 그대로 보존해 재처리 가능
- 마켓 등록은 **규칙을 먼저 검사해 보낼 필요 없는 요청을 걸러내고**, 페이로드 해시로 재전송을 멱등하게 만듭니다
- 마켓이 성공을 주면서 상품ID를 비워 보내면 **성공으로 기록하지 않습니다** — 조용히 어긋나는 데이터를 만들지 않기 위해
- 반품비 상한처럼 응답을 받아봐야 아는 반려는 **메시지를 보정 규칙에 매칭해 고친 뒤 재전송** — 규칙마다 1회, 셀러 값을 올리거나 상품명을 바꾸지 않습니다

> 정규화 실패를 예외로 던졌더니 같은 트랜잭션에서 기록한 `FAILED` 가 함께 롤백되어
> 작업이 동시 실행 슬롯을 영구 점유하던 결함이 있었습니다.
> 통합 테스트가 `@Transactional` 로 감싸져 있어 잡지 못했고, 실제 서버를 띄워서야 드러났습니다.
> 반환값 기반으로 바꾸고, 회귀 테스트는 일부러 트랜잭션 없이 작성했습니다.
> ([관련 내용](https://github.com/JaeHyeokSim/sourcing-pipeline#설계에서-신경-쓴-것))

### 기억에 남는 작업

- **다중 사이트 수집기** — 사이트마다 다른 DOM/전역 객체 구조를 어댑터로 분리해, 신규 사이트 추가 시 기존 코드를 건드리지 않도록 정리
- **오픈마켓 업로드 큐** — 마켓별 API 응답이 제각각이라 실패 유형을 분류하고 재전송 동선을 별도 화면으로 분리
- **크롬 확장 ↔ 서버 브릿지 표준화** — 확장 ID 하드코딩을 걷어내고 `postMessage` ping 감지 방식으로 통일해, 확장 버전이 달라도 안전하게 열화되도록 변경
- **마켓 반려 자동 보정** — 호출부 6곳에 흩어진 보정을 API 호출 래퍼 한 곳으로 모으고, 고정 문구 대신 패턴으로 판정해 마켓이 문구를 바꿔도 대응. 실제 전송 이분 탐색으로 진짜 원인 확정
- **호출 한도·대시보드 성능** — 응답 헤더 기반 감속으로 429를 5회 중 4회에서 0회로, N+1·인덱스 미사용 집계 제거로 대시보드 84.5초→4.1초 / 42초→1초대
- **AI 에이전트 이슈 처리** — Claude Code 에이전트가 사내 이슈를 조사·수정·커밋까지 처리하는 파이프라인 구축, 4주간 단독 처리 230건. 최종 승인은 사람만
- **정기결제 전환** — PG의 카드 등록/청구 분리 정책에 맞춰 0원 빌링키 발급 후 별도 청구하는 흐름으로 재설계, 멱등 처리로 중복 청구 차단
